# 11교시 — 토글 #4(온도) + 가드레일 파이프라인으로 정리

> **이 교시가 끝나면** 마지막 도구(온도 변환)가 붙고, 지금까지 8~10교시에서 **흩어져 있던 검문소**(존재 확인 · 인자 검증 · 안전 실행 · 정책 · 빈도 제한)가 **정해진 순서로 통과시키는 하나의 파이프라인**으로 정리됩니다. 핸들러는 이제 함수 **하나만** 부르면 됩니다.

---

## 0. 이 교시에 만드는 것 (한눈에)

도구가 늘면서 가드레일도 늘었습니다. 지금은 빈도 제한은 핸들러에서(`rate_limit_error`), 인자 검증·실행은 `run_tool`에서, 정책(허용 목록)은 도구 안에서 각각 처리됩니다. **여러 곳에 흩어져** 있어, 순서를 놓치거나 한 도구만 빠뜨리기 쉽습니다.

이 교시에는 이 검문소들을 **한 줄(파이프라인)**로 꿰어, 모든 도구가 **같은 순서로** 통과하게 만듭니다.

```
모델 요청 → dispatch_tool(limiter, name, arguments)
   ├─ 1) 빈도 제한   (rate limit)     ← 가장 싼 거부 먼저
   ├─ 2) 존재 확인   (unknown tool?)
   ├─ 3) 인자 검증   (check_required)
   └─ 4) 실행        (정책 위반은 여기서 ValueError로 잡힘)
        → 결과 또는 에러(JSON)
```

마지막 도구로 **온도 변환 `convert_temperature`**(섭씨↔화씨↔켈빈)를 넣습니다. 4개 도구가 모두 같은 파이프라인을 지나갑니다.

> ⚠️ **정리(refactor)의 목표**: 동작은 그대로 두고 **구조만** 하나로 모읍니다. 그래서 "누락된 검사"나 "도구마다 다른 순서" 같은 실수가 사라집니다.

---

## 🧭 잠깐, 배경지식

이 교시의 핵심인 **파이프라인(pipeline)**과 정리 기법을 짚습니다.

**① 파이프라인(pipeline).** 여러 단계를 **정해진 순서로 차례차례** 통과시키는 구조입니다. 공장 컨베이어의 검사 라인처럼, 각 단계가 "통과/탈락"을 판정하고, 한 단계라도 탈락하면 뒤 단계로 가지 않고 멈춥니다(단락, short-circuit).

**② 순서가 중요하다.** 검문의 순서는 아무래도 좋은 게 아닙니다. **싸고 빠른 거부를 앞에** 둡니다. 예를 들어 빈도 제한은 계산이 거의 없으니 맨 앞에 두어, 초과 요청을 **비싼 실행 전에** 걸러냅니다. 실제 실행(외부 API·계산)은 가장 마지막에 둡니다.

**③ 단일 진입점(single entry point).** 흩어진 검사를 한 함수로 모으면, 부르는 쪽(핸들러)은 그 함수 **하나만** 알면 됩니다. 새 검사를 추가할 때도 파이프라인 한 곳만 고치면 모든 도구에 일괄 적용됩니다. "여기저기 고치다 하나를 빠뜨리는" 실수가 사라집니다.

**④ 리팩터링(refactoring)은 동작을 바꾸지 않는다.** 이 교시의 정리는 **동작을 그대로 유지**한 채 구조만 바꾸는 리팩터링입니다. 그래서 기존 테스트가 **여전히 초록**이어야 합니다. 새 파이프라인에는 새 테스트를 더하되, 8~10교시 테스트는 하나도 깨지지 않아야 합니다.

> 💡 아래에서 파이프라인의 각 단계와 순서를 코드로 봅니다.

## 1. 개념 빠르게 잡기

### 파이프라인 단계와 순서

> | 순서 | 단계 | 어디서(기존) | 실패 시 |
> |---|---|---|---|
> | 1 | 빈도 제한 | 핸들러 `rate_limit_error`(10교시) | 안내 에러, 즉시 중단 |
> | 2 | 존재 확인 | `run_tool`(8교시) | `unknown tool` 에러 |
> | 3 | 인자 검증 | `run_tool`+`check_required`(9교시) | 누락 에러 |
> | 4 | 실행 | `run_tool`(핸들러) | 정책 위반 시 `ValueError`→에러 |

> 이 표의 흩어진 단계를 **`dispatch_tool` 하나**로 모읍니다. 기존 `run_tool`은 2~4단계를 이미 담고 있으므로, 앞에 1단계(빈도)를 붙여 완성합니다.

### 핸들러는 한 줄

> 정리 후 핸들러의 `_handle_tool_call`은 `dispatch_tool(...)` **한 번**만 부르고 결과를 돌려주면 끝입니다. 빈도·검증·실행 순서를 핸들러가 신경 쓸 필요가 없어집니다.

**🟢 구현** — `src/voice_agent/adapter/temperature.py`

```python
SUPPORTED = {"C", "F", "K"}   # 허용 목록: 섭씨·화씨·켈빈


def _to_celsius(value: float, unit: str) -> float:
    """어떤 단위든 일단 '섭씨'로 바꾼다(중간 기준점)."""
    if unit == "C":
        return value
    if unit == "F":
        return (value - 32) * 5 / 9      # 화씨 → 섭씨
    return value - 273.15                # 켈빈 → 섭씨


def _from_celsius(celsius: float, unit: str) -> float:
    """섭씨를 목표 단위로 바꾼다."""
    if unit == "C":
        return celsius
    if unit == "F":
        return celsius * 9 / 5 + 32       # 섭씨 → 화씨
    return celsius + 273.15               # 섭씨 → 켈빈


def convert_temperature(value: float, from_unit: str, to_unit: str) -> float:
    """온도를 from_unit에서 to_unit으로 변환한다. 지원 밖 단위면 ValueError."""
    src = from_unit.strip().upper()       # 정규화(공백·대소문자 통일)
    dst = to_unit.strip().upper()

    # 🛡️ 허용 목록 검사.
    for unit in (src, dst):
        if unit not in SUPPORTED:
            raise ValueError(f"지원하지 않는 단위: {unit} (지원: {sorted(SUPPORTED)})")

    # 섭씨를 '가운데 기준'으로 삼아 두 단계로 변환(from → C → to).
    celsius = _to_celsius(value, src)
    result = _from_celsius(celsius, dst)
    return round(result, 2)
```


> 💡 **가운데 기준점 기법.** 단위가 3개면 조합이 6가지(3×2)라 일일이 다 짜면 번잡합니다. 대신 **섭씨를 중간 허브**로 삼아 "무엇이든 → 섭씨 → 무엇이든" 두 단계로 처리하면, 단위가 늘어도 변환 함수 두 개만 손보면 됩니다.

## STEP 3 — 🔴🟢 가드레일 파이프라인 `dispatch_tool` (TDD)

흩어진 검문을 **정해진 순서**로 통과시키는 단일 진입점을 만듭니다. 기존 `run_tool`(2~4단계)에 빈도 제한(1단계)을 앞에 붙입니다.

**🔴 테스트** — `tests/adapter/test_dispatch.py`

```python
import json

from voice_agent.adapter.tools import dispatch_tool
from voice_agent.domain.rate_limiter import RateLimiter


def _fresh_limiter():
    # 넉넉한 한도(테스트가 빈도에 안 걸리게).
    return RateLimiter(max_calls=100, window_seconds=10)


def test_dispatch_success():
    out = dispatch_tool(_fresh_limiter(), "get_weather", {"city": "서울"})
    parsed = json.loads(out)
    assert "result" in parsed


def test_dispatch_unknown_tool():
    out = dispatch_tool(_fresh_limiter(), "no_such", {})
    assert "error" in json.loads(out)


def test_dispatch_missing_argument():
    out = dispatch_tool(_fresh_limiter(), "get_weather", {})   # city 누락
    parsed = json.loads(out)
    assert "error" in parsed
    assert "city" in parsed["error"]


def test_dispatch_policy_error():
    out = dispatch_tool(_fresh_limiter(), "convert_currency",
                        {"amount": 1, "from_currency": "USD", "to_currency": "XYZ"})
    assert "error" in json.loads(out)


def test_dispatch_rate_limited_first():
    # 한도 1로 두면, 2번째 호출은 '빈도 제한'에서 먼저 막힌다.
    limiter = RateLimiter(max_calls=1, window_seconds=10)
    assert "result" in json.loads(dispatch_tool(limiter, "get_current_time", {}))
    out = dispatch_tool(limiter, "get_current_time", {})
    parsed = json.loads(out)
    assert "error" in parsed
    assert "잦습니다" in parsed["error"]      # 빈도 제한 메시지
```

```python
def dispatch_tool(limiter, name: str, arguments: dict) -> str:
    """가드레일 파이프라인: 빈도 → (존재 → 인자 → 실행)을 순서대로 통과시킨다."""
    # 1) 빈도 제한 — 가장 싼 거부를 맨 앞에. 초과면 즉시 중단.
    denied = rate_limit_error(limiter, name)
    if denied is not None:
        return denied
    # 2~4) 존재 확인 · 인자 검증 · 실행은 run_tool이 이미 순서대로 처리한다.
    return run_tool(name, arguments)
```

```powershell

```

**예상 출력** (🟢): `5 passed`

> 💡 **왜 빈도 제한을 맨 앞에?** 초과 요청은 **아무 일도 하기 전에** 막는 게 가장 쌉니다. 반대로 실제 실행(외부 API·계산)은 비용이 크니 가장 뒤에 둡니다. `run_tool`은 이미 "존재 → 인자 → 실행" 순서를 담고 있어, 그 앞에 빈도만 얹으면 파이프라인이 완성됩니다.

> ⚠️ **설계 선택**: 여기서는 빈도 제한을 **존재/검증보다 앞**에 둬, 잘못된 이름을 반복 호출하는 남용도 빈도에 걸리게 했습니다. 반대로 "정상 호출만 세고 싶다"면 빈도를 뒤로 옮길 수 있습니다. 파이프라인이 한 곳이라, 순서를 바꾸는 것도 이 함수만 고치면 됩니다.

## STEP 4 — 🔵 핸들러 정리: 한 줄로 (REFACTOR)

핸들러의 `_handle_tool_call`을 `dispatch_tool` **한 번** 호출로 바꿉니다. 동작은 그대로, 코드는 단순해집니다.

**바꾸기 전**(10교시): 빈도 확인과 실행이 따로였습니다.

```python
    async def _handle_tool_call(self, fc: dict) -> None:
        denied = rate_limit_error(self._limiter, fc["name"])   # 빈도(따로)
        if denied is not None:
            await self._session.send_tool_result(fc["call_id"], denied)
            await self._session.request_response()
            return
        output = run_tool(fc["name"], fc["arguments"])          # 실행(따로)
        ...
```

**바꾼 후**: 파이프라인 하나로 통일.

```python
    async def _handle_tool_call(self, fc: dict) -> None:
        # 가드레일 파이프라인 한 줄: 빈도 → 존재 → 인자 → 실행을 한 번에.
        output = dispatch_tool(self._limiter, fc["name"], fc["arguments"])
        print(f"\n[도구] {fc['name']}({fc['arguments']}) → {output}", flush=True)
        # 결과(정상이든 에러든)를 모델에 돌려주고 최종 응답을 요청.
        await self._session.send_tool_result(call_id=fc["call_id"], output=output)
        await self._session.request_response()
```

네 도구가 모두 같은 파이프라인을 지납니다.

- **"섭씨 100도는 화씨로 몇 도야?"** → `[도구] convert_temperature(...)` → "212도예요."
- **"지금 몇 시야?" / "서울 날씨" / "3 곱하기 7" / "100달러 원화로"** → 각각 정상.
- **아무 도구나 빠르게 반복** → 빈도 제한에 걸려 잠시 안내.

**예상 출력** (터미널, 예시):

```text
[연결됨] 도구 5개 활성
[도구] convert_temperature({'value': 100, 'from_unit': 'C', 'to_unit': 'F'}) → {"result": "100°C = 212.0°F"}
섭씨 100도는 화씨 212도예요.
```

> ⚠️ **관찰형 확인**: 완성 신호는 **"네 종류 질문이 각 도구로 처리되고, 모든 도구가 같은 가드레일(빈도·검증·정책)을 지난다"**입니다. (변환·파이프라인 로직은 STEP 1~3에서 이미 TDD로 검증했습니다.)

## 📖 용어 사전 (이 교시 신규)

- **파이프라인(pipeline)**: 여러 단계를 정해진 순서로 차례로 통과시키는 구조.
- **단락(short-circuit)**: 앞 단계에서 탈락하면 뒤 단계를 실행하지 않고 멈추는 것.
- **단일 진입점(single entry point)**: 여러 처리를 한 함수로 모아, 부르는 쪽이 그것만 알게 하는 설계.
- **리팩터링(refactoring)**: 동작은 그대로 두고 코드 구조만 개선하는 작업.
- **가운데 기준점(허브)**: 여러 변환을 "무엇→기준→무엇"으로 단순화하는 중간 표준(여기선 섭씨).
- **절대영도**: 이론상 가장 낮은 온도(0K = 약 −273.15°C). 그 미만은 물리적으로 불가능.

```python
import voice_agent.adapter.tools as tools_mod
from voice_agent.domain.rate_limiter import RateLimiter


def test_rate_limit_short_circuits_execution(monkeypatch):
    calls = {"n": 0}

    def fake_time():
        calls["n"] += 1                 # 실제 실행되면 카운터 증가
        return "시각"

    # get_current_time을 카운터 함수로 바꿔치기(monkeypatch).
    monkeypatch.setitem(tools_mod.TOOL_HANDLERS, "get_current_time", fake_time)

    limiter = RateLimiter(max_calls=1, window_seconds=10)
    tools_mod.dispatch_tool(limiter, "get_current_time", {})   # 1번째: 실행됨(n=1)
    tools_mod.dispatch_tool(limiter, "get_current_time", {})   # 2번째: 빈도 초과 → 실행 안 됨

    assert calls["n"] == 1             # 두 번째는 함수에 닿지 않았다
```

**🟢 구현**: 추가 코드 없이 통과합니다. `dispatch_tool`이 빈도 초과 시 `return`으로 **단락**하기 때문입니다.
